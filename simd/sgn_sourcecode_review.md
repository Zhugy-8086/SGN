# SGN 源码问题分析报告

> **项目**：[github.com/Zhugy-8086/SGN](https://github.com/Zhugy-8086/SGN)
> **分析对象**：`simd/` 内核层（量化 SIMD 原语 + CPUID 分派）
> **分析方法**：真实源码精读 + 沙盒编译构建 + 性能基准（bench_v2，对照 `-O3` 朴素标量，全程 bit-exact 验证）
> **重要说明**：本报告**只收录经「源码 + 构建日志」双重验证、确实属于源码本身的问题**。此前几轮误判为「源码 bug」的若干条目（静态库循环依赖、标量声明缺失、bench 命名空间等），经核对 `build.log` 后已**撤回**，不列入下文。

---

## 一、结论先行

源码里**真实存在且值得说的问题共 4 个**，性质各不相同：

- **①②** 是**契约 / 架构层面的脆弱性**：功能没错，但靠注释兜底，未来易烂。
- **③** 是**唯一有实测数字支撑的真·性能缺陷**：`decode_i16_f32` 实测 0.75×（SIMD 反不如标量）。
- **④** 是**工程成熟度缺口**：偏偏最该测的 `decode` 没有专用测试。

> **一句话总结**：内核的**数值正确性（bit-exact）经实测是过硬的**；问题集中在**架构契约脆弱、指令集命名失配、稀疏布局热路径负优化、测试覆盖缺口**这 4 处。

## 三、源码里的 4 个真实问题

### 问题 ①：`avx512` 符号靠注释维系编译契约（架构脆弱性 · 中）

**位置**：`simd_dispatch.cpp`（约 97–103 行）

```cpp
// avx512 符号由 avx512.cpp（单独编译单元）提供，本文件仅声明
extern "C" const Dot16Fn dot16_avx512;
extern "C" const Dot8Fn  dot8_avx512;
extern "C" const Dot4Fn  dot4_avx512;
```

**问题描述**：

这些符号的**定义**位于 `avx512.cpp`，靠**文件级 `-mavx512f` 编译选项**（CMake 单独给这个文件加 flag）才能产出。也就是说——

- 符号**是否存在、能否链接成功**，完全取决于 **CMake 文件级选项配对正确**；
- `simd_dispatch.cpp` 自身**没有任何 `static_assert` 或构建期检查**来保证这一点。

**风险**：

一旦 CMake 那条文件级选项失效，或链接器裁剪了 `avx512.cpp` 的翻译单元（TU），就会出现：

```
undefined reference to `dot16_avx512`
```

本次构建侥幸编过，但**「声明–定义契约靠注释维系、不靠机制强制」是典型的脆弱设计**——换平台、换构建系统、做裁剪链接时极易翻车。

**建议修复方向**：

- 用 `static_assert` / 构建期断言显式校验符号存在；
- 或将 avx512 后端封装为独立可选组件，缺失时编译期明确报错而非静默。

---

### 问题 ②：`ssse3.cpp` 文件名与实际指令集不符（可维护性 · 低）

**位置**：`simd/ssse3.cpp`（文件头注释）

```cpp
// 注意：batch_reverse_u8 使用 _mm256_*（实际需 AVX2）
// 当前构建全局 -mavx2，故此处可用；若严格 SSSE3 构建需拆分
__m256i _mm256_shuffle_epi8(...);   // ← 明明是 AVX2 的 256 位版本
```

**问题描述**：

- 文件名叫 `ssse3.cpp`，暗示「此文件仅需 SSSE3」；
- 但其中的 `batch_reverse_u8` **实际使用的是 `_mm256_*`（AVX2 指令）**；
- 作者自己在头注释里承认了这一点，还注明了修复日期。

**后果**：

任何**阅读者**、**静态分析工具**，或未来想做「严格 SSSE3 构建」的人，都会**按文件名误判这个文件只需 SSSE3**。作者目前不得不靠**运行时检测**（`#if __AVX2__`）和**注释**来兜底。

**性质**：功能正确，但**文件命名与指令集语义自相矛盾**，可维护性差。

**建议修复方向**：

- 将 AVX2 部分（`batch_reverse_u8`）拆分到 `avx2.cpp`，`ssse3.cpp` 只保留真正的 SSSE3 路径；
- 或直接将文件重命名为与其实际指令集相符的名字，消除歧义。

---

### 问题 ③：`decode_i16_f32` 稀疏布局下的 SIMD 负优化（性能缺陷 · 高）

**位置**：`simd/avx2.cpp`（约 110–182 行，decode 的 AVX2 热路径）

```cpp
// 每个 uint64：低 16 位有效，高 48 位无效（见 line 112 注释）
for (; i + 7 < n_values; i += 8) {
    __m256i v0 = _mm256_loadu_si256(pv_ptr + i);       // 加载 32 字节
    __m256i v1 = _mm256_loadu_si256(pv_ptr + i + 4);   // 再加载 32 字节
    // PSHUFB + PALIGNR + PMOVSXWD 洗牌...
    _mm256_storeu_ps(&res_ptr[i], ...);                // 只存 8 个 float
}
```

**问题根因**：

数据布局**极度稀疏**——每 8 字节中只有**低 2 字节有效**，但 SIMD 路径：

- 每个迭代做了 **2 次 load**；
- 加上**重洗牌**（PSHUFB / PALIGNR / PMOVSXWD）；
- 最终**只产出 4 个有效 float**。

对照**标量锚点**（同一文件的 scalar 路径）：

```cpp
int16_t val = pv & 0xFFFF;
res = (float)val * scale;   // 一位与 + 一转换，无洗牌
```

标量路径几乎**零洗牌开销**，而 SIMD 路径的洗牌开销盖过了并行收益。

**实测佐证**（bench_v2，bit-exact 验证正确）：

```
decode_i16_f32:  speedup = 0.67 ~ 0.95×（所有尺寸，稳定低于 1×）
```

即 **SIMD 路径在所有测试尺寸上都不如朴素标量**。

**性质**：这是 **4 个问题中唯一有实测性能数字支撑的源码缺陷**——在「每 uint64 仅低 16 位有效」的稀疏布局下，重洗牌的 AVX2 解码是**负优化**。按当前公开契约（高 48 位无效），属于**热路径设计错误**。

**建议修复方向**：

- 改用 `vpcompress` / 掩码提取有效 int16，减少无效字节参与运算；
- 或针对稀疏布局走**更窄的 SSE 路径**；
- 或改换数据布局（让有效数据连续 packed），从根本上消除每字节利用率低的问题。

---

### 问题 ④：测试矩阵不完整（工程成熟度 · 低）

**证据**：`build.log` 显示 ctest 只跑了 2 个测试：

```
100% tests passed (2/2)
  Test #1: madd512_logic_test
  Test #2: simd_boundary_test
```

**问题描述**：

仓库里**没有任何针对以下原语的专用正确性测试**：

| 缺失测试的原语 | 备注 |
|---|---|
| `sum_f32` | 实测 ~17×（最快的原语，却无专属测试） |
| `decode_i16_f32` | 实测 0.75×（**恰好是性能异常的那一个**） |
| `accum_f32` | 无 |
| `reverse_bytes8` | 无 |
| `batch_reverse_u8` | 无 |

**讽刺点**：**性能最异常、最需要测试覆盖的 `decode_i16_f32`，恰恰是测试矩阵里的空白**。如果没自己写 `bench_v2`，这个 0.75× 的回退**永远不会被发现**。

**性质**：不算功能 bug，但属于**工程成熟度缺口**——直接影响项目对回归的防护能力。

**建议修复方向**：

- 为每个公开原语补齐对照标量锚点的 bit-exact 正确性测试；
- 优先补 `decode_i16_f32` 与 `sum_f32`（性能敏感、且已发现异常）。

## 五、核心价值判断

- **数值正确性**：bit-exact 分派、`-32768` 溢出回退、强制 scalar 回退精确 1.00×——**这些是源码里最见功底、且经实测过硬的部分**。
- **性能**：除 `sum_f32`（~17×）外，主要原语稳态加速有限（dot16 ~5.5×），且 `decode` 存在明确的负优化。**作者宣称的 72–95× 是特定小尺寸 + 特定硬件的峰值，不具备一般性。**
- **工程成熟度**：缺构建系统（已由外部 CMake 补全）、测试覆盖不全、指令集契约靠注释——这是项目从「内核原型」走向「可交付库」的主要障碍。

> **一句话**：作者把「量化点积内核」做到了**数值严谨、分派规整**，但**性能热路径（decode）存在实测缺陷，且工程脚手架与测试体系尚未收尾**。值得动手修的只有 **③（decode 负优化）**——修复后有望让该原语在稀疏布局下也必胜标量。

| 原语 | 稳态加速（大向量 N≥4096） | 峰值 |
|---|---|---|
| `dot16`（INT16 点积） | ~5.5× | 10.5× / 39.8 Gops @K=4096 |
| `sum_f32`（FP32 归约） | ~17× | 19.6× |
| `decode_i16_f32` | **0.75×（比标量慢）** | 异常 |
